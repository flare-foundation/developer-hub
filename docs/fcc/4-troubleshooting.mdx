This page covers common issues you may hit when building [Flare Compute Extensions](/fcc/overview) with the [FCE Go scaffold](https://github.com/flare-foundation/fce-go-scaffold) and the [`fce` CLI](https://github.com/flare-foundation/fce-tooling).

Flare Confidential Compute is still in development, and the Coston2 deployment changes as it progresses.
Start with `fce status`, which compares your extension's deployment record with the chain:

```bash
fce status -chain coston2 ./template
```

It shows the contracts, the extension ID, the allowed versions, the governance, and the machines in production with their URLs.
It also warns while the test hash is allowed.

## `fce` Refuses to Run

| Symptom                                                                  | What to do                                                                                                                                                                                                                                                          |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fce` refuses the fork because of its version                            | The fork's `fce-version` file names the `fce` versions it supports, such as `v0.1`. Install a matching `fce` release, or merge the latest scaffold `main` into your fork. Development builds only warn.                                                             |
| A check fails with `(recommended)`                                       | It's a recommendation, not a requirement. To deviate on purpose, add a file named `fce-i-know-what-im-doing` to the extension directory with your reason as its text, or pass `-i-know-what-im-doing`. `fce` then warns instead of failing, and prints your reason. |
| `fce add-version` complains about uncommitted changes                    | Others must be able to rebuild the image from your fork. Commit first. This is a recommendation, so the i-know-what-im-doing mode also turns it into a warning.                                                                                                     |
| `fce run` refuses to start because of a previous run                     | The previous machine was not paused onchain. Run `fce stop` with the same chain, account, and directory, then start again.                                                                                                                                          |
| `fce run` reports that another machine of the extension is in production | Sends can be routed to that machine, and if it no longer runs, it never answers. Pause it: run `fce stop` if `fce run` started it, or have its owner call `MachineManager.pause`.                                                                                   |
| `fce run` refuses your `-rpc` URL                                        | `tee-proxy` reads the chain through the same RPC from inside its container, so the URL cannot be on loopback. Use a reachable host, or pass `-indexer-db`.                                                                                                          |

## Machine Never Reaches Production

`fce run` registers the machine, waits for the attestation result, requests an availability check, and calls `toProduction`.
If it stops partway, check the following.

- **The signing policy is behind.**
  The proxy's `lastSigningPolicyId` must reach the chain's current reward epoch before the machine can register.
  Shortly after a reward epoch changes this can take a few minutes.
  Check it with `curl -s <proxy>/info | jq .teeInfo.lastSigningPolicyId`.
- **The challenge expired.**
  `fce run` warns and asks for a new challenge once the old one expires.
  Let it continue.
- **Missing versions or governance.**
  A test machine needs a test version (`fce add-version -test`) and a governance (`fce governance`).
  The machine attests to the governance hash, so the onchain signers and threshold must match exactly.
  `fce run` takes them from your deployment record.
- **The account is not an allowed extension owner.**
  `fce deploy` calls `register`.
  The call succeeds when the deployer is an allowed extension owner, or when allow-all is on.
  Otherwise it reverts with [`OwnerNotAllowed`](/fcc/reference/ITeeCommonErrors#ownernotallowed).
  See [Owner allowlists](/fcc/owner-allowlists).
- **The account is not an allowed machine owner.**
  `fce deploy` allows the deployer.
  If you run machines from a different account, the extension owner must allow it first.
  See [Owner allowlists](/fcc/owner-allowlists).
- **Not enough funds.**
  Registration and the availability check charge fees, and every step pays gas.
  Top up from the [Coston2 faucet](https://faucet.flare.network/coston2).
- **No system machine to run the check.**
  If `fce run` reports that extension 0 has no machine in production, the network cannot run availability checks right now.
  Try again later, or contact [support](https://flare.network/resources/technical-support).
- **A slow host.**
  On Apple Silicon, Docker emulates `linux/amd64`, so the build and startup are slower.
  `-host-platform` lets Docker choose the platform instead.

Each `tee-node` start generates a new key, so each run registers a new machine.
A machine registered by an earlier run stays in its last onchain state until someone pauses it.

### After a Protocol Redeploy

If Flare redeploys `Relay`, `FlareSystemsManager`, or `VoterRegistry`, stop the machine (Ctrl-C, or `fce stop`) and start a new one with `fce run`.
`tee-proxy` reads those addresses from the [Flare contract registry](/network/guides/flare-contracts-registry) at each start, so there is no config to edit.

If the redeploy also cleared extension registrations, `fce status` shows the mismatch.
Run `fce deploy` again to finish what is missing.

## Sends Revert

These come from `ExtensionBase` and `FlareTeeManager` when you call a send function such as `myCommand`:

| Error                               | Cause                                                                                                                                                                                 |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `TooMany()`                         | No machine of the extension is in production, so there is no TEE to send to. [`quoteFee`](/fcc/instruction-fees#quotefee) also reverts with it. Start one with `fce run`.             |
| `ExtensionIdNotSet()`               | `setExtensionId` was never called. Run `fce deploy` again, which runs `PostRegister.s.sol`.                                                                                           |
| `InsufficientFee(price, available)` | The call paid less than its instructions cost. Pay at least [`quoteFee(opType, opCommand)`](/fcc/instruction-fees#quotefee) per TEE. `fce send` finds the fee by simulating the call. |
| `TeeMachineNotAvailable`            | A TEE you named isn't in production right now.                                                                                                                                        |
| `TeeNotFound`                       | An address you named isn't a TEE at all.                                                                                                                                              |
| `DuplicateTee`                      | The same TEE appears twice in the list.                                                                                                                                               |
| `EmergencyPauseActive`              | The extension is under an emergency pause.                                                                                                                                            |
| `NotCharging` / `NestedCharge`      | `_send` was called outside a `chargesFees` function, or one `chargesFees` function called another.                                                                                    |

## Results Show an Error

A handler's error becomes the result log `error: <text>`, with `status 0`.

| Log                                    | Cause                                                                                                                                                                                                                                       |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `error: invalid payload`               | The payload didn't decode. `payload.DecodeABI` accepts only the canonical encoding, and `payload.DecodeJSON` rejects unknown fields. Check that the contract's `abi.encode` and the Go `abi.Arguments` agree, then regenerate the fixtures. |
| `error: no handler for this op`        | The op pair reached the extension but isn't registered on that channel. Check the names, and check that an instruction op uses `RegisterInstructionHandler` and a direct op uses `RegisterDirectHandler`.                                   |
| `error: deadline exceeded`             | The handler took longer than 1.5 seconds. Return a `Run` to continue in the background, as the [External API guide](/fcc/guides/external-api-extension) shows.                                                                              |
| The result stays at `status 2` forever | The TEE restarted during a long-running job. Results from that job are lost, so consumers must time out pending results.                                                                                                                    |

## Instructions Never Reach Your Extension

### Symptoms

- The instruction is accepted onchain, and you get an instruction ID back.
- The instruction never arrives at your extension, and polling the action result returns `404`.
- Other instructions from the same extension relay and round-trip normally.

### Root Cause: Reserved Operation Names

Operation names are shared between the system and custom extensions, and part of that space is reserved.

The `F_` prefix is reserved for system operation types.
The platform refuses op types that start with `F_` from custom extensions, and the scaffold's library panics if you register one.
These types exist in the system, each with a fixed set of commands:

| Operation type | Purpose                                   |
| -------------- | ----------------------------------------- |
| `F_REG`        | TEE attestation and registration          |
| `F_WALLET`     | Key generation, backup, restore, and VRF  |
| `F_GET`        | Read-only queries such as TEE info        |
| `F_POLICY`     | Signing policy initialization and updates |
| `F_GOVERNANCE` | Machine path list management              |
| `F_XRP`        | XRPL payments and reissues                |
| `F_BTC`        | Bitcoin payments and reissues             |
| `F_FDC2`       | FDC2 proving                              |

:::warning
The command names those types use are reserved too, including `TEE_ATTESTATION`, `TEE_INFO`, `TEE_BACKUP`, `KEY_GENERATE`, `KEY_INFO`, `KEY_PROOF`, `KEY_DELETE`, `KEY_DIRECT_BACKUP`, `KEY_DIRECT_RESTORE`, `KEY_DATA_PROVIDER_RESTORE`, `INITIALIZE_POLICY`, `UPDATE_POLICY`, `SET_MACHINE_PATH_LIST`, `PAY`, `REISSUE`, `VRF`, and `PROVE`.
:::

A custom op type that does not start with `F_` can still reuse one of those reserved command names, and the pair passes local validation.
This failure gives you no error at all: the instruction is simply not delivered to a custom extension.

### Solution: Name Operations After Your Own Domain

Choose op type and command strings that are specific to your extension, and do not reuse a system command name even with a custom type.
Descriptive names also make instructions easier to identify onchain.

## Test Machines Versus Production

`fce run` starts `tee-node` in test mode (`MODE=1`).
The machine attests to `tee-node`'s fixed test code hash on `TEST_PLATFORM`, which says nothing about the code it runs.
Only attestation differs: the contracts, data providers, and instruction flow are real.
You do not need Confidential Space hardware, a paid cloud account, or an indexer to work through the guides.

Contracts still accept a test machine's signatures, even though its operator holds its key.
Keep the test version off any extension that real users use, or disable it with `fce disable-version -test` before they arrive.

A production machine runs the attested image on a Confidential Space VM, on a platform you allowed with `fce add-version -platform GCP_AMD_SEV,GCP_INTEL_TDX`.
`fce` registers test machines.
[Deploy a TEE on Google Cloud](/fcc/guides/deploy-on-gcp) starts the image with the [FCC node suite Terraform](https://github.com/flare-foundation/fcc-node-suite-deployment).
The scaffold's [production draft](https://github.com/flare-foundation/fce-go-scaffold/blob/main/docs/production.md) lists the registration calls that are still being checked on a live machine.

## Coming From the Legacy Scaffold

Earlier guides used the multi-language `fce-extension-scaffold` with shell scripts, `TeeExtensionRegistry` and `TeeMachineRegistry` addresses from a JSON file, and a required indexer database.
The FCE Go scaffold replaces that flow:

| Legacy                                                                                   | Now                                                                                                      |
| ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `TeeExtensionRegistry` and `TeeMachineRegistry` addresses from `deployed-addresses.json` | `FlareTeeManager`, resolved from the [Flare contract registry](/network/guides/flare-contracts-registry) |
| `pre-build.sh`, `post-build.sh`, `test.sh`                                               | `fce deploy`, `fce add-version`, `fce governance`, `fce run`, `fce send`, `fce direct`                   |
| Indexer database required for `ext-proxy`                                                | `tee-proxy` reads the chain through the RPC by default, and `-indexer-db` is optional                    |
| `SIMULATED_TEE=true`                                                                     | Test mode with `fce add-version -test` and `fce run`                                                     |
| Go, Python, and TypeScript implementations                                               | A Go library, plus a language-agnostic wire protocol that `fce conformance` checks                       |

Port your handlers into a fork of the new scaffold rather than patching addresses in the old one.

## Getting Further Help

The scaffold's [docs](https://github.com/flare-foundation/fce-go-scaffold/tree/main/docs) cover the rules, the trust model, and testing in depth.

If none of the above resolves your issue, ask through [technical support](https://flare.network/resources/technical-support) or on [X](https://x.com/FlareDevs).
Include your extension ID, the TEE machine address, the instruction ID that failed, and the output of `fce status`.
